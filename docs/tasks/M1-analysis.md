# M1 — Аналіз

**Мета:** `wave analyze ./data/library` заповнює базу, і цим даним
можна вірити.

Оцінка: 3–5 вечорів. Це найбільш "науковий" мілстоун — тут найбільше
шансів застрягти на відладці. Тому `wave inspect` (T1.7) роби рано,
а не в кінці.

Референс: [02-audio-analysis.md](../02-audio-analysis.md)

---

## T1.1 — Скан бібліотеки

- [ ] рекурсивний обхід папки, розширення: `.mp3 .flac .wav .m4a .ogg`
- [ ] sha256 файлу — **тільки перші й останні 1 МБ + розмір**, а не
      весь файл. На 1000 треків повний хеш — це хвилини I/O без користі
- [ ] теги через `mutagen`: title, artist, album, duration
- [ ] якщо тегів немає — розпарсити з імені файлу
      (`Artist - Title.mp3`), не падати
- [ ] upsert у `tracks` по `file_path`; якщо `file_hash` змінився —
      скинути `analyzed_at`
- [ ] `wave scan <path>` окремою командою від `analyze`

**Готово:** `SELECT count(*) FROM tracks` збігається з кількістю файлів.

## T1.2 — Пайплайн фіч, крок 1: спектральні

- [ ] `analysis/spectral.py`
- [ ] завантаження: `librosa.load(path, sr=22050, mono=True)`
- [ ] STFT `n_fft=2048, hop_length=512`
- [ ] centroid, rolloff(0.85), bandwidth, flatness, contrast, ZCR
- [ ] MFCC 20 коефіцієнтів
- [ ] повертати dataclass `SpectralFeatures` з покадровими масивами
- [ ] тест: синусоїда 440 Гц → centroid ≈ 440; білий шум → flatness → 1

**Не забудь:** `mfcc[0]` викидається з вектора схожості (це гучність,
не тембр). Але у `.npz` зберігай усі 20 — раптом знадобиться.

## T1.4 — Крок 3: темп і біти

- [ ] `analysis/rhythm.py`
- [ ] `onset_strength` → `beat_track(units='time')`
- [ ] корекція октави: `<70` → ×2, `>180` → ÷2
- [ ] `bpm_confidence` через автокореляцію onset-огинаючої:
      відношення головного піка до другого
- [ ] downbeat: серед бітів знайти той, що дає максимум енергії
      sub-смуги при групуванні по 4. Простий і робочий підхід:
      для кожного зсуву `k in 0..3` порахувати суму `band_energy[sub]`
      на бітах `k, k+4, k+8, ...`, взяти максимум
- [ ] `first_beat_sec`, масив `beats`, масив `downbeats`
- [ ] тест: метроном 120 BPM → `bpm == 120 ± 0.5`

**Це місце, де ти витратиш найбільше часу.** Не воюй за ідеальність:
для 80% електронної музики librosa дає правильний BPM з першого разу,
а решту вручну поправиш у UI пізніше. Заведи в `tracks` поле для
ручного оверрайду BPM — воно врятує нерви.

**Правило, яке варто закласти зараз:** `bpm` — це метадана для
фільтрації й відображення. Джерело правди про позиції бітів — **масив
`beats`**, і ніде в коді позиція біта не рахується як
`first_beat + n / bpm`. Для електроніки різниці немає, для живого
запису до кінця треку набігає до півсекунди. Один рядок різниці
зараз — і не доведеться переписувати beat-alignment, коли додаси рок.

## T1.7 — `wave inspect` (роби рано!)

- [ ] `wave inspect <track_id> [--plot out.png]`
- [ ] у консоль: BPM + confidence, ключ + Camelot + confidence, LUFS,
      тривалість, список сегментів
- [ ] у PNG (matplotlib, 3 підграфіки):
  1. спектрограма (dB) з вертикальними лініями бітів і жирнішими —
     downbeat'ів
  2. 8 смуг енергії у часі
  3. RMS-огинаюча з підсвіченими межами сегментів

**Це не «nice to have».** Без цієї картинки ти будеш дивитись на
числа й гадати. З нею одразу видно, що біти зсунуті на півтакту або
що сегментація порізала не там.

- [ ] `wave normalize-features` окремою командою

- [ ] записати в `feature_stats`

різних масштабах, якщо нормалізувати на льоту. Косинусна відстань
на ненормалізованих фічах дає сміття.

## T1.10 — Оркестрація і паралель

- [ ] `wave analyze <path> [--force] [--workers N]`
- [ ] пропускати треки з `analyzed_at IS NOT NULL` і актуальним
      `analysis_version`, якщо не `--force`
- [ ] `multiprocessing.Pool`, за замовчуванням `cpu_count() - 1`
- [ ] прогрес-бар через `rich`
- [ ] помилка на одному треку не валить весь прогін: лог + продовжити
- [ ] у кінці — зведення: скільки оброблено, скільки впало, час

**Пастка:** psycopg-з'єднання не можна ділити між процесами. Кожен
воркер відкриває своє, або (простіше) воркери повертають результат
у головний процес, і він пише в БД сам.

## Валідація мілстоуна

Не закривай M1, поки не пройдено все:

- [ ] **BPM.** 5 треків із відомим BPM (Beatport, теги, ручний
      підрахунок) — розбіжність < 1%
- [ ] **Ключ.** трек у C-major і трек у A-minor дають `8B` і `8A`
- [ ] **Детермінізм.** той самий трек двічі → однакові числа
- [ ] **Спектрограма.** на `wave inspect --plot` біти лягають на
      транзієнти
- [ ] **Об'єм.** 50+ треків проаналізовано без падінь
- [ ] **Швидкість.** трек 4 хв — не довше 30 сек на одному воркері

Записуй треки, де аналіз промахнувся, у нотатку **«Wave — Журнал
аналізу»** в Obsidian (`Pet проекти/Wave/`) — там уже є шаблон запису
і таблиця треків-еталонів. По одному промаху патерн не видно; коли
назбирається 15–20, стане зрозуміло, чи це проблема жанру, параметра
чи гіпотези в алгоритмі.
