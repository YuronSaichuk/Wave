# M1 — Аналіз

**Мета:** `wave analyze ./data/library` заповнює базу, і цим даним
можна вірити.

Оцінка: 3–5 вечорів. Це найбільш "науковий" мілстоун — тут найбільше
шансів застрягти на відладці. Тому `wave inspect` (T1.7) роби рано,
а не в кінці.

Референс: [02-audio-analysis.md](../02-audio-analysis.md)

---

## T1.1 — Скан бібліотеки

- [x] рекурсивний обхід папки, розширення: `.mp3 .flac .wav .m4a .ogg`
- [x] sha256 файлу — **тільки перші й останні 1 МБ + розмір**, а не
      весь файл. На 1000 треків повний хеш — це хвилини I/O без користі
- [x] теги через `mutagen`: title, artist, album, duration
- [x] якщо тегів немає — розпарсити з імені файлу
      (`Artist - Title.mp3`), не падати
- [x] upsert у `tracks` по `file_path`; якщо `file_hash` змінився —
      скинути `analyzed_at`
- [x] `wave scan <path>` окремою командою від `analyze`

**Готово:** `SELECT count(*) FROM tracks` збігається з кількістю файлів.

## T1.4 — Крок 3: темп і біти

- [x] `analysis/rhythm.py`
- [x] `onset_strength` → `beat_track(units='time')`
- [x] корекція октави: `<70` → ×2, `>180` → ÷2
- [x] `bpm_confidence` через автокореляцію onset-огинаючої:
      відношення головного піка до другого
- [x] downbeat: серед бітів знайти той, що дає максимум енергії
      sub-смуги при групуванні по 4. Простий і робочий підхід:
      для кожного зсуву `k in 0..3` порахувати суму `band_energy[sub]`
      на бітах `k, k+4, k+8, ...`, взяти максимум
- [x] `first_beat_sec`, масив `beats`, масив `downbeats`
- [x] тест: метроном 120 BPM → `bpm == 120 ± 0.5`

**Це місце, де ти витратиш найбільше часу.** Не воюй за ідеальність:
для 80% електронної музики librosa дає правильний BPM з першого разу,
а решту вручну поправиш у UI пізніше. Заведи в `tracks` поле для
ручного оверрайду BPM — воно врятує нерви.

**Правило, яке варто закласти зараз:** `bpm` — це метадана для
фільтрації й відображення. Джерело правди про позиції бітів — **масив
`beats`**, і ніде в коді позиція біта не рахується як
`first_beat + n / bpm`. Для електроніки різниці немає, для живого
запису до кінця треку набігає до півсекунди. Один рядок різниці
зараз — і не доведеться переписувати beat-alignment, коли додаси рок.

воркер відкриває своє, або (простіше) воркери повертають результат
у головний процес, і він пише в БД сам.

## Валідація мілстоуна

Не закривай M1, поки не пройдено все:

- [ ] **BPM.** 5 треків із відомим BPM (Beatport, теги, ручний
      підрахунок) — розбіжність < 1%
- [ ] **Ключ.** трек у C-major і трек у A-minor дають `8B` і `8A`
- [ ] **Детермінізм.** той самий трек двічі → однакові числа
- [ ] **Спектрограма.** на `wave inspect --plot` біти лягають на
      транзієнти
- [ ] **Об'єм.** 50+ треків проаналізовано без падінь
- [ ] **Швидкість.** трек 4 хв — не довше 30 сек на одному воркері

Записуй треки, де аналіз промахнувся, у нотатку **«Wave — Журнал
аналізу»** в Obsidian (`Pet проекти/Wave/`) — там уже є шаблон запису
і таблиця треків-еталонів. По одному промаху патерн не видно; коли
назбирається 15–20, стане зрозуміло, чи це проблема жанру, параметра
чи гіпотези в алгоритмі.
