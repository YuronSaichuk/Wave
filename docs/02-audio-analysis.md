# 02. Аудіо-аналіз

## Базові параметри

Фіксуємо один раз і не міняємо без бампу `analysis_version`:

```python
SAMPLE_RATE = 22050   # librosa default; для аналізу вище не треба
N_FFT       = 2048    # ~93 мс вікно — компроміс частота/час
HOP_LENGTH  = 512     # ~23 мс крок → 43 кадри/сек
WINDOW      = 'hann'
```

Чому 22050, а не 44100: половина частот, удвічі менше роботи, а все
цікаве (тембр, гармонія, ритм) лежить нижче 11 кГц. Для **рендеру
міксу** аудіо читається окремо у повній якості — там даунсемпл
неприпустимий.

Чому 2048/512: з `n_fft=2048` роздільна здатність по частоті — 10.8 Гц,
чого досить, щоб розрізняти ноти вище ~E2. Нижче баси зливаються, але
для басу нам потрібна енергія смуги, а не точна нота. Перекриття 75%
(hop = n_fft/4) — стандарт, дає гладку огинаючу.

## Що рахуємо

### Крок 1 — STFT

```python
y, sr = librosa.load(path, sr=SAMPLE_RATE, mono=True)
S = np.abs(librosa.stft(y, n_fft=N_FFT, hop_length=HOP_LENGTH))
S_db = librosa.amplitude_to_db(S, ref=np.max)
```

`S` — це і є "розклад по Фур'є": матриця `[1025 частот × N кадрів]`.
Усе далі — похідні від неї.

### Крок 2 — спектральні дескриптори (тембр, "як звучить")

| Ознака | Функція | Що означає |
|---|---|---|
| Spectral centroid | `librosa.feature.spectral_centroid` | "центр ваги" спектру — суб'єктивна яскравість |
| Spectral rolloff | `spectral_rolloff(roll_percent=0.85)` | частота, нижче якої 85% енергії — скільки верхів |
| Spectral bandwidth | `spectral_bandwidth` | розкид навколо центроїда — вузький тон чи шум |
| Spectral flatness | `spectral_flatness` | 0 = чистий тон, 1 = білий шум. Ловить перкусію і дисторшн |
| Spectral contrast | `spectral_contrast` | різниця пік/впадина по смугах — "чіткість" міксу |
| Zero-crossing rate | `zero_crossing_rate` | грубий індикатор шумності; дешевий, тримаємо |
| MFCC (20) | `mfcc(n_mfcc=20)` | стиснуте представлення тембру. **Головна фіча для схожості** |

MFCC — це, по суті, форма спектральної огинаючої в мел-шкалі,
розкладена по косинусах. Два треки з близькими MFCC звучать схоже
за фактурою, навіть якщо в різних тональностях.

**Важлива деталь:** `mfcc[0]` — це загальна гучність, не тембр. Для
пошуку схожості його треба **викидати або нормалізувати окремо**,
інакше пошук буде знаходити просто однаково гучні треки. Беремо
`mfcc[1:20]`, а гучність тримаємо окремо через LUFS.

### Крок 3 — енергія по смугах (для схожості і для світла)

Ділимо спектр на 8 логарифмічних смуг:

```python
BANDS_HZ = [
    (20,    60),    # sub        — де живе бочка
    (60,   150),    # bass       — бас-лінія
    (150,  400),    # low-mid    — тіло інструментів
    (400, 1000),    # mid        — вокал, снейр
    (1000,2500),    # high-mid   — розбірливість
    (2500,5000),    # presence   — атака, "різкість"
    (5000,8000),    # brilliance — хай-хети
    (8000,11000),   # air
]
```

Для кожного кадру — сума енергії в смузі, в дБ, згладжена. Це дає
матрицю `[8 × N кадрів]`, яка потім буквально стає основою світлової
доріжки: sub → рівень червоного стробу, brilliance → мерехтіння
білого і т.д. Ця сама матриця, усереднена по треку, іде в `band_vec`.

### Крок 4 — ритм

```python
onset_env = librosa.onset.onset_strength(y=y, sr=sr, hop_length=HOP_LENGTH)
tempo, beats = librosa.beat.beat_track(
    onset_envelope=onset_env, sr=sr, hop_length=HOP_LENGTH, units='time')
```

Три пастки, з якими зіткнешся:

1. **Октавна помилка.** librosa часто дає 85 замість 170 або навпаки.
   Лікується так: якщо `tempo < 70` — множ на 2; якщо `> 180` — ділі
   на 2. І окремо: зберігай **обидва** варіанти (`bpm` і `bpm*2`) при
   пошуку сусідів, бо трек на 128 і трек на 64 міксуються чудово.

2. **Впевненість.** Порахуй автокореляцію `onset_env` і візьми
   відношення головного піка до другого — це `bpm_confidence`.
   Треки з confidence < 0.5 (амбієнт, живі записи) не варто
   міксувати beat-aligned переходом, для них потрібен довгий фейд.

3. **Тактова сітка ≠ сітка бітів.** Для гарного переходу потрібні межі
   **фраз** — 16 або 32 біти. Знайди downbeat (перший біт такту) через
   `librosa.beat.plp` або за максимумом енергії sub-смуги на бітах,
   і від нього будуй фразову сітку.

Зберігаємо: `bpm`, `bpm_confidence`, `first_beat_sec`, повний масив
`beats` (у .npz), індекси downbeat'ів.

### Крок 5 — гармонія і тональність

```python
chroma = librosa.feature.chroma_cqt(y=y, sr=sr, hop_length=HOP_LENGTH)
```

`chroma_cqt` краще за `chroma_stft` для визначення тональності —
constant-Q дає логарифмічну шкалу, що відповідає нотам.

Тональність — через **профілі Krumhansl-Schmuckler**: усередни хрому
по треку, скоррелюй з 24 еталонними профілями (12 мажорних + 12
мінорних, кожен — циклічний зсув), візьми максимум. Різниця першого
і другого місця — це `key_confidence`.

Далі мапимо в **Camelot** (див. 03), бо саме в цій нотації зручно
рахувати гармонійну сумісність.

### Крок 6 — гучність

```python
import pyloudnorm as pyln
meter = pyln.Meter(sr)
lufs = meter.integrated_loudness(y)
```

LUFS (ITU-R BS.1770) — не RMS і не пік. Це перцептивна гучність, і саме
її треба вирівнювати при міксі, інакше один трек буде "вистрибувати".
Ціль для сету: **-14 LUFS integrated** (стандарт стрімінгу).

Також рахуємо `lufs_range` (динамічний діапазон) — трек з великим LUR
має тихі місця, придатні для входу наступного треку.

### Крок 7 — структура треку

Найкорисніше і найменш очевидне. Потрібне, щоб знати, **де в треку
можна різати**.

```python
# self-similarity matrix по MFCC + chroma
R = librosa.segment.recurrence_matrix(features, mode='affinity', sym=True)
boundaries = librosa.segment.agglomerative(features, k=8)
```

Результат — 6–10 сегментів із часовими межами. Для кожного рахуємо
середню енергію і label за евристикою:

- перший сегмент із низькою енергією → `intro`
- сегменти з максимальною енергією → `drop` / `chorus`
- останній із спадною енергією → `outro`
- сегмент із енергією нижче медіани в середині треку → `breakdown`

Це не musicology-grade, але для вибору точки переходу вистачає:
**виходимо з `outro` або кінця `chorus`, входимо в `intro` або
`breakdown`**.

## Формат зберігання

### У БД (`track_features`)

Тільки агрегати і вектори — те, за чим шукаємо.

```
timbre_vec (40) = concat(mean(mfcc[1:20]), std(mfcc[1:20]))
                  → z-score по всій бібліотеці → L2-нормалізація
chroma_vec (12) = mean(chroma) → L2-нормалізація
band_vec   (8)  = mean(band_energy_db) → z-score
```

**Нормалізація по бібліотеці — окремий крок**, не частина аналізу
одного треку. Тримай `feature_stats` (mean/std кожної координати)
у таблиці або JSON-файлі й перераховуй, коли бібліотека виросла
істотно. Інакше вектори перших 10 треків і наступних 1000 будуть
у різних масштабах.

### У кеші (`data/cache/<track_id>.npz`)

Усе покадрове, `float32`, стиснуто:

```python
np.savez_compressed(path,
    band_energy = band_energy,     # [8 × N]  → світло
    rms         = rms,             # [N]      → огинаюча
    onset_env   = onset_env,       # [N]      → переходи
    beats       = beats,           # [B]      сек
    downbeats   = downbeats,       # [D]      сек
    chroma      = chroma_ds,       # [12 × M] даунсемпл до 5 Гц
    mfcc        = mfcc_ds,         # [20 × M] даунсемпл до 5 Гц
)
```

Даунсемпл chroma/mfcc до 5 Гц зменшує файл у ~9 разів, а для аналізу
структури і переходів роздільної здатності 200 мс достатньо.
`band_energy` і `onset_env` лишаємо у повних 43 Гц — вони потрібні
світлу і beat-alignment.

Орієнтир розміру: трек 4 хв → ~1.5 МБ. 1000 треків → 1.5 ГБ. Прийнятно.

## Продуктивність

Аналіз 4-хвилинного треку на звичайному CPU: **10–25 секунд**, з них
левову частку з'їдають `chroma_cqt` і `recurrence_matrix`.

Оптимізації, коли набридне чекати:

- `librosa.load` — найповільніше на MP3. Перекодуй бібліотеку у
  22050 Hz mono WAV один раз, аналізуй з нього.
- Паралель по треках через `multiprocessing.Pool` — лінійно
  масштабується, бо librosa GIL-bound усередині numpy.
- `recurrence_matrix` на довгих треках — O(N²). Даунсемпл фічі до
  5 Гц **перед** побудовою матриці, а не після.

## Валідація

Не довіряй результату, поки не перевірив на очевидних кейсах:

- Візьми 5 треків, де ти точно знаєш BPM (є в тегах або на Beatport),
  і звір. Розбіжність більше 1% — щось не так із hop_length.
- Візьми трек у C-major і трек у A-minor — вони мають дати той самий
  Camelot (8B і 8A відповідно, тобто сусіди).
- Побудуй спектрограму і накладай на неї детектовані біти. Якщо вони
  не лягають на транзієнти — дивись `first_beat_sec`.
- Прогони той самий трек двічі — результат має бути побітово
  ідентичний. Якщо ні — десь недетермінований seed.
